# Windows bench baseline — pull_request runs (Issue #687)

# Source: "Benchmark (Windows)" workflow run 41989213058 (pull_request
#         event, 2026-11-05) — the BENCHMARK SUMMARY table only.
#
# Why a second baseline: GitHub Actions `pull_request` runs and
# `push`/`schedule` runs land on measurably different runner
# hardware. Over 6 runs of each (2026-10-29 … 2026-11-09) every
# pull_request run was faster than every push/schedule run, on
# every workload:
#
#                Get-Content 100M.bin   Concurrent 4x 10M.bin
#   push/schedule      6.60 … 7.64s          1.80 … 2.06s
#   pull_request      3.62 … 5.98s          1.02 … 1.89s
#
# Same-day pairs differ by up to 40% (2026-11-09: a pull_request run
# at 3.616s vs push runs at 6.597s / 6.915s), so this is a property
# of the event, not of the date. Comparing a pull_request run against
# the push/schedule baseline would therefore flag every PR as a
# ~35% regression, and comparing a push/schedule run against this
# baseline would flag every merge as a ~40% regression.
#
# The workflow picks the baseline that matches the event:
# bench/baseline-windows.txt for push/schedule/workflow_dispatch,
# this file for pull_request.
#
# This run is the slowest of the observed pull_request runs for the
# two heavy critical workloads, so the gate only fires above a value
# never seen before in this context.
#
# Regenerating: dispatch the "Benchmark (Windows)" workflow, download
#   the `bench-result-windows` artifact, and copy its BENCHMARK
#   SUMMARY table into the matching baseline file.
#
# Gate: bench/check-regression.ps1 compares the critical tests against
#   this file with a 20% threshold, plus a 0.1s baseline noise floor
#   and a 0.1s minimum absolute slowdown. See that script for the
#   measured numbers.
